The Architecture I Wish I Knew Five Years Ago

Layered folders, domain boundaries, and the one rule that saved me from a 90,000-line utils file — plus the refactor playbook I now run on every codebase I inherit.

NU
Naruto Uzumaki Published Oct 2, 2026 · 11 min read · 1,284 claps

On this page

Every codebase I have inherited had the same tombstone: a folder called utils. It started with three functions and ended with nine hundred — date formatting next to payment signatures, a React hook, two regexes nobody understood, and a deepMerge that ran on the critical path of checkout. Nothing was technically wrong. Everything was structurally doomed.

Five years and four greenfield builds later, I have a short list of structural decisions I make on day one. They are unglamorous, they survive rewrites, and they are the reason adding a feature now costs an afternoon instead of a fortnight.

The problem with “flat and tidy”

The instinct on a new project is to organise by technical role: one folder for components, one for hooks, one for services, one for types. It looks tidy on day one. By month six, changing anything touches all four folders, and no single human holds the whole feature in their head.

Warning

If your components/ directory has more than ~40 entries, you are grouping by type, not by meaning. That is the first sign the structure is fighting the product.

The fix is not a fashionable architecture pattern. It is a simple alignment: organise around the nouns of your product, and let the technical roles live inside each noun.

One rule: features own their code

Don't design your folder structure around the framework's vocabulary. Design it around the vocabulary your users and product managers actually use. — the rule that changed how I review pull requests

In practice that means a feature folder contains everything that feature needs — UI, state, data access, tests and even types. If you can delete a feature by deleting one directory, your structure is right.

A folder shape that scales

Here is the shape I reach for on almost every application:

text 
src/
├── app/                 # shell: routing, providers, layout
├── features/
│   ├── billing/
│   │   ├── components/  # only used by billing
│   │   ├── api/         # queries + mappers
│   │   ├── hooks/
│   │   ├── billing.types.ts
│   │   └── billing.test.ts
│   ├── projects/
│   └── auth/
├── shared/
│   ├── ui/              # design-system primitives
│   ├── lib/             # truly generic helpers
│   └── config/
└── server/              # API routes + domain logic

Two directories deserve a rule of their own. shared/ is a promotion target: code may only move there after it is used by at least two features — never before. And utils is banned outright; a helper lives next to the one caller it has.

Where the boundaries go

Boundaries are cheap when they are enforced by the bundler and expensive when they are enforced by a wiki page. I encode them twice: once in the folder layout, once in lint rules.

TypeScript 
// features/billing/api/invoices.ts
import { z } from "zod";
import { http } from "@/shared/lib/http";

export const InvoiceSchema = z.object({
  id: z.string().uuid(),
  totalCents: z.number().int().nonnegative(),
  status: z.enum(["draft", "open", "paid", "void"]),
  issuedAt: z.string().datetime(),
});

export type Invoice = z.infer<typeof InvoiceSchema>;

export async function listInvoices(projectId: string) {
  const raw = await http.get(`/projects/${projectId}/invoices`);
  return InvoiceSchema.array().parse(raw);
}

Boundaries are cheap when they are enforced by the bundler and expensive when they are enforced by a wiki page. I encode them twice: once in the folder layout, once in lint rules that fail the build:

JSON 
{
  "no-restricted-imports": ["error", {
    "patterns": [
      {
        "group": ["../features/*"],
        "message": "Import from your own feature folder only."
      },
      {
        "group": ["**/utils/**", "**/helpers/**"],
        "message": "Co-locate helpers with their single caller."
      }
    ]
  }]
}

The schema is the contract. If the server changes a field, the parse fails in development with a readable message instead of shipping a blank cell to customers.

The four-step refactor

When I inherit a tangled codebase, I never big-bang it. Instead:

  1. Pick one vertical slice — usually the flow with the most bugs. Anything users complain about weekly is a good candidate.
  2. Move it behind a seam — relocate its files into a feature folder without changing a single line of logic. Pure git mv plus import fixes.
  3. Prove parity — run the existing tests, then add two: one for the happy path, one for the failure path you are most scared of.
  4. Delete the residue — the old utils entries with one caller go. Dead abstractions are debt with interest.
  • Keep each slice to a single pull request, reviewable in under 30 minutes.
  • Never mix behaviour changes with a move.
    • That includes “tiny” cleanups you spotted along the way.
    • Do those in a follow-up PR with its own tests.
  • Track progress as slices migrated, not lines moved.
Success

On the last migration, twelve PRs across three weeks took a 148-file feature from “nobody knows where things live” to a single folder with 91% test coverage. Zero incidents during the move.

How to measure it

Structure is hard to quantify, but these four numbers moved in the right direction after every migration I have run:

Before vs. after the feature-folder migration (12-week window)
Metric Before After Change
Median PR review time 4h 12m 1h 48m −58%
Files touched per feature 19 7 −63%
Rollback rate 6.4% 2.1% −67%
“Where does this live?” questions in Slack ~30 / week ~4 / week −87%

The last row is my favourite. Onboarding time for new engineers dropped from two weeks to four days, mostly because the answer to “where does this live?” became obvious from the feature name.

Tip

If you use a monorepo, the same rule scales to packages: enforce the direction with your workspace graph, not with a paragraph in the README. Press Ctrl + K in your editor to jump between definitions and check imports quickly.

Steal this checklist

Run it before your next architecture review:

  • Can I delete a feature by deleting one folder?
  • Does every file have exactly one obvious reason to change?
  • Are cross-feature imports caught by a lint rule, not by memory?
  • Is shared/ smaller this month than it was last month?
  • Would a new hire answer “where does billing live?” in under ten seconds?
Don't do this

Never migrate in a freeze-and-pray big bang. The six-month branch that reorganises everything is where features go to die and merge conflicts go to multiply. Small slices, always.

Structure is not about aesthetics — it is about how cheaply your team can change its mind. Pick one feature this week, move it, measure the difference, and write down what you learned. If you want the exact lint configuration we use for boundaries, it is published in the Rasengan UI repository.
